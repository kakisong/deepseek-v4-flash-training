DeepSeek-V4-Flash 模型特点

V4-Flash 是 DeepSeek V4 系列的 long-context / sparse-attention 变体。和 V3 / R1 同代相比,核心差异在 attention 路径和 MoE 极致稀疏两个方向上同时下了重手 —— 这两点决定了训练路径的所有特殊性。

1.1 关键参数

维度值说明

AttentionMLA + tilelang sparse-MLA第 0/1/42 层 dense MLA,中间 40 层 sparse(top-128 blocks / 4-token compress)
q-lora / kv-lora1024 / 512低秩压缩,显著降 KV cache 与 attention 通信量

权重格式(发布)HF FP8(per-tile 128×128)训练前需 dequant 到 BF16 再切分

1.2 工程上跟 V3 的关键差异

  • 43 层质数:常用 PP 因子 (4/8/16) 都不整除,简单 VPP API --num-layers-per-virtual-pipeline-stage 几何上不可解。必须走 --pipeline-model-parallel-layout 显式 16-stage 字符串布局,或借 --decoder-first/last-pipeline-num-layers 微调首尾 — V3 的常规模板搬不过来
  • sparse-MLA bwd 是新 kernel:走 tilelang 自定义 kernel,Megatron 的 selective recompute hook、checkpoint wrapper 都不接。所有"按层 / 按 op selective"的 activation 节省思路在 V4 上几何阻塞
  • Attention 通信稀疏化:q-lora/kv-lora 压缩让 CP ring 通信量比 V3 同 seq 下降 ~50%,反过来也让 CP 收益相对于 PP/TP 更明显
  • 40 层全 MoE:EP all-to-all 是稳定瓶颈而非偶发热点。dispatcher 选择(alltoall vs DeepEP)直接决定 -5% 量级 wall
  • HF FP8 → Megatron BF16 转换是一次性大坑:涉及 megablocks 命名映射 / per-tile FP8 dequant / torch_dist 分片三段,本项目踩了 11 次失败迭代

一句话:V4-Flash 的训练难度不是"参数多",而是"常规并行假设大量失效" — 43 层 + sparse-MLA + 全 MoE 联合作用,迫使每一档 shape 都要重新做切卡推导。

为什么选 miles 来跑 SFT

SFT 任务理论上有很多框架可选。最终选了 miles(RLHF 框架,退化模式跑 SFT),不是因为它在 SFT 上比专用 SFT 框架强,而是因为团队接下来要做 RL,提前在同一套框架下把 SFT 跑通,RL 阶段就不需要再换框架 / 重切卡 / 重做权重转换。

verl 为什么"勉强"

verl 是字节开源的 RLHF 框架,设计目标是 SPMD + FSDP 路径,跑中小 dense 模型(7B-70B)上效率很高。但放到 V4-Flash(284B / 43 层全 MoE / sparse-MLA)上,有四道几何 / 工程门槛同时卡住,逐个看:

门槛verl 现状V4-Flash 需求差距
主干并行路径 FSDP / FSDP2(zero-3 风格)为一等公民,Megatron 后端是后加且对 MoE 支持滞后 必须 TP=8 PP=16 EP=8 联立,FSDP 在 284B 上权重 + grad shard 跨节点 allgather 是 step-time 杀手 FSDP 在 H20 IB 200 Gbps 上 allgather 284B/16 ≈ 18 GB/step 已经接近 PP send/recv 一个数量级,跑不到当前 5.23s 量级
MoE EP 实现成熟度 FSDP 路径下 EP 走的是 token dispatcher 简化版,没有 alltoall + DeepEP 的 dispatcher 选择 40 层全 MoE,EP a2a 是稳定瓶颈;DeepEP backend(NVL/IB overlap)在本方案上拿到 -5.2% wall verl 缺 DeepEP 集成,也缺 --moe-token-dispatcher-type flex + fp32 router 这一层 sweep 空间
43 层质数 + PP layout FSDP 路径下不显式分 PP stage;Megatron 后端的 PP 走 verl 自己包的 layer 分配,没有 --pipeline-model-parallel-layout 显式字符串布局 43 层无法被 PP=16 整除,必须显式 16-stage layout 才能避开"中间 stage 多 1 层"造成的 bubble 倾斜 需要自己改 verl 的 PP partitioner,跟上游分叉
sparse-MLA / V4 plugin verl 不接 miles_plugins 这一层 hook,也没 MEGATRON_SPARSE_ATTN_IMPL 切换 tilelang sparse-MLA 是 V4 唯一可行的 long-seq 路径,kernel 通过 plugin 注入到 Megatron attention layer 等于把 V4 模型代码 + tilelang kernel 在 verl 里重新接一遍,工程量以周计且需要持续 follow 上游
cpu-offload Adam + dist-ckpt FSDP 路径有 CPU offload,但跟 Megatron-style dist-ckpt 不兼容 40 GB Adam state(8 节点)必须 cpu-offload;ckpt 要走 torch_dist 给后续 RL 阶段复用 切框架后 ckpt 格式不通,SFT → RL 之间多一道格式转换

verl 不是"差",而是"假设和 V4-Flash 错位"。它的设计选型(FSDP first、SPMD、dispatcher 简化)在 7B-70B dense + 中等 RL workload 上是最优的;但当模型同时具备:284B 总参 + 43 质数层 + 全 MoE + sparse-MLA + 长 seq + 大 Adam state 这五个特征,FSDP 路径的几何收益消失,反而要补齐 verl 当前没有的 PP layout / DeepEP / V4 plugin / Megatron dist-ckpt 四块拼图 —— 加起来比直接用已经原生支持这一切的 miles 多花几周以上。

更关键的是 verl 当前在 H20 上 V4-Flash 量级的工业实测数据基本没有(社区跑的最大公开 case 是 70B dense + DP=8),没有可参考的 baseline 意味着所有性能调优都要自己摸,而 miles 已经被 V4 团队和 R1 团队踩过路。

2.2 选 miles 的三个核心理由

V4 模型支持是 miles 唯一原生具备的

V4-Flash 模型代码不在 miles 主仓,而是通过 PYTHONPATH=$V4_MEGATRON(radixark/Megatron-LM 的 dsv4-pr28 分支)+ miles_plugins(外部 wheel)注入。这个注入路径是 V4 团队上游已经维护的 — 任何其他框架都需要自己重新对接 sparse-MLA kernel、MoE router、权重 layout,工程量以周计且需要持续 follow 上游。

SFT → RL 复用同一套切卡 / ckpt / 集群脚本

本方案 SFT 跑出来的 torch_dist ckpt、TP/PP/EP/CP 切卡布局、Ray 集群拉起脚本,RL 阶段 100% 复用。换框架意味着 ckpt 要再做一次格式转换、切卡要重测、集群要重建 —— 项目时间表上不可承受。

6 个 flag 把 RL 退化成 SFT,不动框架源码一行

这是 miles 框架本身的设计美感:rollout 函数、loss 函数、advantage 计算都做成了可热插拔组件。SFT 在 miles 看来就是"rollout 不调推理引擎、loss 不算 KL、weight sync 切断"的一个特例。具体 6 个 flag 见 §3.1。

关于"用 RL 框架跑 SFT 是否有抽象税":理论上比专用 SFT 框架多了一些抽象(rollout pod、placement_group、Ray queue)。实测这些在 SFT 模式下基本零开销 —— rollout pod 退化成纯 CPU dataloader,Ray queue 一步一通,GPU 几乎被 actor 独占。付出的"框架抽象税"远小于换框架的迁移成本。

方案描述

3.1 RL 如何降级到 SFT

miles 原生执行图是 RLHF 闭环:rollout pod 用 SGLang 做推理 + reward,actor pod 用 Megatron 做 PPO 训练,二者通过 weight sync 闭环。SFT 退化的核心是把这条闭环从三处切开:rollout 不调推理 / loss 不算 KL / weight sync 切断。具体由这 6 个 flag 完成。

Flag源码作用不开会怎样
--rollout-function-path miles.rollout.sft_rollout.generate_rollout hot-swap rollout 函数为纯 CPU tokenize + 构造 loss_mask 默认调 SGLang 推理,SFT 没 prompt-only 数据 → 报错
--loss-type sft_loss select_loss_function() 分派到 sft_loss_function(per-token CE × mask) 默认走 policy_loss(PPO clip + KL),需要 reward / advantage
--calculate-per-token-loss loss 按 token 加权而非 sequence 长 response 欠拟合,短/长 response 权重失衡
--disable-compute-advantages-and-returns 跳过 GAE / return 计算 actor 报 KeyError: 'reward'
--debug-train-only 切断 RL 反馈环,actor / rollout 不再 weight sync actor 卡死等 weight sync
--loss-mask-type deepseek_v4 用 V4 chat template token 边界识别 prompt / response 用错 mask,prompt token 被算入 loss

退化后的数据流(纯顺序,无 RL 闭环):

parquet
   → [Rollout pod, 纯 CPU]
       V4 chat template render → tokenize → 构造 loss_mask → Ray queue
   → [Actor pod, GPU]
       Megatron forward (TP×PP×EP + tilelang sparse-MLA) → CE × loss_mask
       → backward → cpu-offload Adam → 每 N 步 torch_dist ckpt

RL 框架的 reward / advantage / weight sync 整条链路全部短路,但 rollout pod / placement_group / Ray queue 仍然存在 —— miles 的执行图还是 RL 那张图,只是数据通路和 loss 函数被替换。这就是为什么"不动源码一行"能成立。

3.3 切卡推导

三档 shape(4K / 32K / 64K)的并行配置不是试出来的,是被三个不等式联立倒推出来的唯一解:

  • 等式约束:TP × PP × CP × DP × world_replica = N_GPU
  • 容量约束:每 rank 显存 = weights + Adam state + activation peak ≤ 95 GB(H20)/ 141 GB(H200)
  • 带宽约束:TP / EP 走节点内 NVLink,PP / CP 跨节点走 IB(200 Gbps RoCE)

为什么是 PP=16

这是本方案最关键的发现。2026-05-21 集群从 8 节点扩到 16 节点,先后试了三种用法:

方案4K step timevs 8 节点 prod (10.88s)verdict
16 节点 DP=2 + ZeRO-1 + 关 offload(同 shape)OOM(86.96 GB allocated)—✗ activation 撑爆
16 节点 DP=2 + ZeRO-1 + offload11.69 s+7.4%✗ DP=2 跨节点 IB allreduce 抵消省的 Memcpy
16 节点 PP=16 + offload5.92 s−45.6%✓ memory 余量大
16 节点 PP=16 + 关 offload(winner)5.23 s−51.9%✓ H4 真正解锁,200 步零漂移,headroom 25%
16 节点 PP=16 + 关 offload + DP=2 ZeRO-16.87 s+31% vs winner✗ Adam 已被 PP 切到 2.5 GB,ZeRO-1 边际收益 < 通信开销

PP=8 → PP=16 让每 rank 持有的 layer 数从 5-6 减到 2-3,三个因子同向叠加:

  • Adam state 折半再折半:40 GB → ~2.5 GB/rank,关 cpu-offload 完全无压力 — 之前在 8 节点上的 H4 假设(95 - 6 - 40 - 46 = -3 GB,装不下)被这一刀直接解锁
  • Activation peak 折半:每 rank 只算 1 stage(VPP 自动 disable,layout 16/16=1)
  • Pipeline 充实度 ×4:GBS=128 / PP=16 = 8 microbatch/stage,vs PP=8 时 2/stage,bubble 摊薄
  • Per-stage 算量减半,fwd/bwd 时间也跟着缩

H20 单卡显存账

项8 节点 PP=816 节点 PP=16

所以 H4("关 cpu-offload Adam")不是"换 H200 才能解锁",而是"PP 翻倍把 Adam 切到能放 GPU 的尺度"。这个解锁路径比 H200 迁移成本低得多 —— 16 节点 H20 已经够。

3.4 关键性能优化决策

方法论:先列假设,再用 trace 验证假设。Trace 是验证工具不是发现工具 —— "NCCL 占 50%" 可能是 PP spin-wait 等待时间,不是真传输。

假设验证方法结果
H1 NCCL/IB 没启,跑 TCP 慢路径ibstatOUT mlx5_bond_* Active 200 Gbps,48% NCCL 是 PP spin-wait
H2 PP=8 → PP=4 减 bubblestep time 对比OUT 慢 22%(per-stage 工作量翻倍)
H3 关 recomputestep / TFLOPS / mem 对比CONFIRM @4K step −10%, TFLOPS +20%, mem −6 GB(反直觉)
H3' 32K shape 上关 recomputestep 0 memREVERSED 32K activation 几何阻塞,必须 full
H4 关 cpu-offload Adam跑 step 08 节点 OOM / 16 节点 PP=16 解锁
H5 attention impl 选型trace 占比OUT 仅 4.5% wall,不是瓶颈
H6 rollout/train 串行trace wait_timePARTIAL 35% wait,需改框架(P0 候选)

H3 反直觉发现

常识里关 recompute = activation 占用增加 = 显存上涨。V4 上反过来:

项recompute=fullrecompute=none
Activation~10 GB(少,recompute 路径)~16 GB(多,resident)
Kernel workspace~12 GB(每 bwd 重分配,allocator churn)~2 GB(复用,no churn)
KV intermediate~5 GB~5 GB
峰值60.0 GB53.6 GB(−6.4 GB)

根因:V4 tilelang sparse-MLA 在 recompute 路径下,bwd 每层重新分配 KV intermediate + kernel workspace。这个动态分配的峰值占用比保留 activation 更费。

H3 反转

activation 与 seq 长度线性相关。32K + PP=4 单 rank activation ~40 GB,把"省 12 GB churn"完全淹没,关 recompute → OOM at 95 GB。profile 结论严格绑定到 shape,跨 seq-length 不能盲移植。

Shaperecompute=full 峰值recompute=none 峰值推荐
4K (TP=8 PP=8 CP=1)60 GB53.6 GBnone
32K (TP=4 PP=4 CP=4)65-70 GBOOM >95 GBfull(forced)
64K (TP=2 PP=4 CP=8)~85 GB—full(forced)

EP 通信优化

Megatron schedule 层 EP all-to-all overlap 需要 V4 attention 提供 backward_dw callable,目前 blocked。改走 DeepEP backend 在 dispatcher kernel 内部 overlap NVL + IB:

--moe-token-dispatcher-type flex --moe-enable-deepep --moe-router-dtype fp32

50 步 × 3 档 SM sweep:SM=20 sweet spot,median 10.88s vs alltoall+bf16 11.48s = -5.2%,variance −17%(stdev 0.85 vs 1.02)。叠加 layout+VPP 累积 -7.6%。已切 prod 默认。NV 官方 NeMo-Automodel yaml 也默认开 DeepEP,跟本方案选型一致。

VPP + 显式 layout

43 是质数,不能被 PP=16 整除。简单 --num-layers-per-virtual-pipeline-stage API 几何上不可解。改走 --pipeline-model-parallel-layout 显式 16-stage 字符串 + interleaved 1F1B,bubble 摊到所有 stage,prod 实测 median 11.48s vs baseline 11.79s = -2.6%(15 步窗口 -7.6%,长跑被 system noise 稀释一些)。

已验证不要做

方案为什么不做
PP=4(从 PP=8 减,以为能减 bubble)per-stage 工作量翻倍,实测慢 22%
DP=2 + ZeRO-1(同 shape,16 节点)跨节点 IB allreduce 抵消省的 Memcpy,实测 +7.4%;叠 PP=16 时 +31% vs winner
32K 上 selective recompute双重阻塞:activation 几何上不允许任何非 full;V4 plugin router 不接 selective hook,触发 requires_grad 断言(moe_utils.py:733)
H20 上 FP8 GEMMH20 FP8 仅 2× BF16(H200 是 4×),ROI 低 + 改动大,留给 H200
关 cpu-offload Adam @ 8 节点显存账 95 - 6 - 40 - 46 = -3 GB,装不下;走 PP=16 路径解锁,不是 H200

5.3 三层 env 正交分解

所有训练任务都通过 cluster/run.sh --fleet X --scale Y --workload Z 三个维度组合启动。三层正交,任意组合都可跑。这套分解是迁移成本控制的核心:换硬件只动 fleet,换 shape 只动 scale,换数据只动 workload,三者互不污染。

层关心什么切换示例
fleet(集群)节点数 / IP / master / NCCL_SOCKET_IFNAME / docker image / 共享存储H20 → H200 = 新建 1 个文件
scale(切卡)TP / PP / CP / EP / PP layout / VPP / DeepEP SM同 shape 不同切卡 = 改一个 flag
workload(任务)数据 / max_tokens / LR / warmup / save_interval / recompute / chat template跨 shape 复用同 scale

加载顺序:base.env → fleet/X.env → hw/$V4_GPU_MODEL.env → scale/Y.env → workload/Z.env → CLI override。后载入的覆盖前者,CLI 优先级最高。

5.4 一键启动

# 1. 拉集群(master 上跑一次)
cd cluster/
bash bring_up_cluster.sh           # 自动 clone miles fork、起 Ray、keepalive

# 2. 4K SFT prod(winner)
bash run.sh \
  --fleet h20_16node \
  --scale tp8pp16ep8_layout \
  --workload sft_prod

# 3. 8 节点 fallback(集群缩水时)
bash run.sh \
  --fleet h20_8node \
  --scale tp8pp8ep8_layout \
  --workload sft_prod_8node

# 4. 32K agent SFT
bash run.sh --fleet h20_16node --scale tp4pp16cp2ep8 --workload sft_albaliang

# 5. 64K 长 context
bash run.sh --fleet h20_16node --scale tp2pp16cp4ep8 --workload sft_64k_pp16

# 6. 一键 profile(任意 preset 加 --profile 即可)
bash run.sh --fleet h20_16node --scale tp8pp16ep8_layout \
  --workload sft_smoke --profile --num-rollout 6 --lr-warmup-iters 0

# 7. 关集群
bash tear_down.sh

5.7 H200 迁移成本

三层正交分解最大的回报:迁移到 H200 时 scale / workload / hw/h200.env 全部不动,只新建 cluster/fleet/h200_16node.env:

export V4_CLUSTER_NAME=h200_16node
export V4_GPU_MODEL=h200            # 自动选 hw/h200.env
export V4_NUM_NODES=16
export V4_MASTER_IP=<H200 master IP>
export V4_WORKER_IPS="<IP2> ... <IP16>"
export V4_WORK=/path/to/shared/storage/v4-sft
export V4_IMAGE=radixark/miles:dev
export V4_DOCKER_MOUNTS=(
  "/path/to/shared:/path/to/shared"
  "/dev/infiniband:/dev/infiniband"
)

之后 --fleet h200_16node 即可,所有 scale / workload preset 100% 复用。
