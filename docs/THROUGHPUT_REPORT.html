目标：在现有 16 节点 128 卡上把推理吞吐和并发拉到最高。 结论：横向 16 副本 + router + cuda graph 方案落地（16/16 在线），聚合峰值 ~42,000 输出 tok/s @ 并发 2,048、0 失败、活跃节点 GPU 利用率 ~100%。 大规模单端点 EP 路线因 sglang 镜像 NVSHMEM-over-RoCE bootstrap 缺陷受阻（见 §5）。

3. 资源利用率

  • 持续负载下，活跃副本节点 GPU 利用率全部 ~100%（均值 ≈ 99.8%）。
  • 每卡显存：权重 ~66GB + KV/cuda-graph ~5GB，常驻 ~71GB / 96GB。

decode batch 与瓶颈：SWA KV 池

实测单副本 conc=256 时 #running-req ≈ 150–220（cuda graph: True，配置上限 256），但 swa token usage = 1.00（满）而 full token usage 仅 0.10。 V4-Flash 是 hybrid SWA 模型（swa_full_tokens_ratio=0.1），实际 decode 批被 SWA(滑窗注意力) KV 池卡住，而非 max_running_requests。 这解释了单副本 conc 128→256 吞吐略降（cuda graph 下 3,705→3,169 tok/s）：到 256 时 SWA 池满、请求开始排队。

mem-fraction-staticmax_total KV空闲显存单副本 conc256 输出 tok/s
0.85（基线）—~14 GB3,169

提高 mem-fraction-static 把更多显存给 SWA KV 池 → 单副本 +20%。已将 run_sglang_replica.sh 默认改 0.92。 注意：全量 16 副本统一切 0.92 需逐副本重载，而本集群 CFS 冷读在并发重载下极慢（~30 MiB/s，单波 5 节点需 15–20 min）， 故全量统一 0.92 留到维护窗口分批滚动（避免同时拉崩服务）；当前为 0.85/0.92 混合，router 无差别负载均衡，功能不受影响。

4. 调优收敛路径（自动迭代）

  1. 验证 16 副本 + router 基线（cuda graph 关）：聚合 21,006 tok/s @ 并发 4096。
  2. 单副本试开 cuda graph → 3.9× 增益（954→3,705 tok/s @ 并发128），V4 + dsv4 attention 后端兼容。
  3. 全量 16 副本切到 cuda graph（页缓存热，重载 ~60s + capture）→ 聚合峰值 42,171 tok/s @ 并发 2,048。
  4. 确认并发拐点：单副本 ~128、16 副本聚合甜点在 ~2,048（128/副本），并发 4,096 仍 0 失败（吞吐回落到 37k）。

5. 为什么不是“大规模 EP 单端点”

首选方案是 DeepSeek 官方推荐的大规模专家并行（DP-attention + DeepEP，128 卡单实例，KV 池暴涨 → batch 拉满）。 软件与形状全部就绪并正确：

  • sglang 0.5.12.post1，--enable-dp-attention --moe-a2a-backend deepep --ep-size 128 --dp-size 128 --nnodes 16 全部接受；
  • 128 卡分布式组建成功（DP0..127）、权重加载完成、DeepEP buffer 构造（“20 SMs”）通过。

受阻点：内网是 RoCE（以太，8×200Gb mlx5_bond），DeepEP 跨节点 all-to-all 依赖 NVSHMEM； 该镜像 NVSHMEM UID bootstrap 的 allgather 读到错乱数据（Message truncated: received N bytes instead of 40 → nvshmem init failed）， 导致首个 forward 卡在 all-to-all（GPU 0% 死等）。这属于上游已知未决问题 （DeepEP #139、sglang #7888 / #12533），与 H20+RoCE 下缺 gdrdrv / nvidia_peermem 内核模块及 IBGDA 驱动配置相关， 非应用层参数可快速绕过。横向副本方案完全规避跨节点通信，故作为交付路线。

EP vs 横向副本（取舍）

大规模 EP 单端点横向 16 副本（已采用）
跨节点通信每 MoE 层 all-to-all（依赖 NVSHMEM/RoCE）无
KV 池 / 单请求长上下文更大（专家摊薄）每副本受限（~权重占 66GB/卡）
聚合吞吐理论上限更高近线性 ~16×，实测稳
稳健性 / 故障隔离单点、调参重副本独立，挂一个不影响其余
本集群可用性受 NVSHMEM-RoCE 阻塞已上线

7. 后续可提升项

  • 更高单请求并发：每副本 max-running-requests 受 V4 默认 256；KV 池足够时可上调（注意 cuda graph bs 上限）。
  • 解锁 EP：在 sglang 镜像内装 gdrdrv/nvidia_peermem + 配置 NVSHMEM IBGDA-over-RoCE（GID idx 3），跑通 2 节点烟雾测试后再上 128 卡。
  • 服务常驻：当前为手动部署（nohup in container）；长期对外建议加进程守护 / health 自愈。
